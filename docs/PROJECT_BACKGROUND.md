# SpireExact 的项目背景

SpireExact 为给定的 Slay the Spire 2 种子寻找一条完整通关路线。输入包括种子、角色、飞升与解锁状态，输出是从新局开始、可以逐步执行和复核的动作序列。

当前研究采用 IRONCLAD / Ascension 10 / all unlocks / fresh start，目标为整局胜利。mode1 全信息允许搜索利用种子决定的未来，持续尝试同一个种子的不同构筑与行动。SpireBoard 前端与命令行的公开 i082 入口默认每次运行 30 分钟，并为每次作业保存设置、身份和资源记录。

作者建议大部分种子选择 45 分钟预算，前端与 CLI 支持 1–45 分钟，默认仍为 30 分钟。这个建议与各版本的实际效果记录分别保存。

## 把整局决定连接起来

战斗结果会影响下一次选牌、商店购买、火堆选择和地图分支。前期形成的牌组决定后期能否通过首领，最终幕第一首领的战后生命与资源又决定第二首领的入场状态。求解器把这些决定接成一条贯穿整局的路线。

Python 规划器管理路线谱系、失败位置和已到达关口，安排偏离、延续与重试。原生 worker 执行完整候选，返回真实后继状态。搜索利用这些观察继续分配算力，直到找到可以从开局复核的获胜动作，或达到当前作业预算。

## 从种子到证书

1. **创建新局。** 使用确定的种子、角色、飞升和解锁状态建立原生游戏状态。
2. **规划完整路线。** 选择地图、奖励、商店、休息和战斗的候选延续，将完整请求交给宿主。
3. **执行游戏规则。** C# 宿主调用用户安装版本的游戏程序集，在离线 TestMode 中执行动作，收集后继状态、决策证据与真实终局。
4. **独立重放。** 获胜候选在新进程中从初始状态完整重放，核对动作、证据、终局和二进制身份，形成证书。

公开动作重放入口还可以在本机构建上执行两个独立新进程的完整重放，生成当前身份下的新证书。

## 三层协作

| 层次 | 职责 |
| --- | --- |
| Python 整局规划 | 候选档案、前缀、路线偏离、关口模型、评估调度与运行记录 |
| C# 原生宿主 | 创建和恢复游戏状态，执行菜单与战斗动作，导出证据与运行身份 |
| CombatSolver | 在固定源码版本上搜索战斗行动，为整局 rollout 提供候选计划 |

规则执行来自用户提供的游戏程序集。CombatSolver 的预测与候选随后进入原生执行和重放流程。固定上游见 [upstream.lock.json](../upstream.lock.json)，harness 补丁、宿主适配、许可证与第三方署名随源码保留。

## 当前 i082 机制

**地图边界检查点。** 搜索保存稳定边界的可恢复状态，使多个候选从同一已到达前缀继续；完整动作序列同时保留从开局重放的路径。检查点绑定完整状态与上下文身份。

**隔离 worker 与有序派发。** 原生进程池管理生命周期、时间和内存额度，协调器按登记顺序吸收常规任务结果；F2 就绪度采样完成即可回传排序信号。独立重放使用新的进程。

**构筑多样性。** 根部策略包括原生与社区统计档位 `pick`、`elo`，派生轨迹保留所属策略。牌组族上限帮助精英池保留多个构筑方向。

**关口计划与投入分配。** 真实首领入场结果更新关口模型，多级战斗计划与接近过关的重试提供候选。F1/F2 就绪度采样、交替精英名额和联合模型给最终幕提供额外排序信号。

**成对选牌探针。** i082 每 32 个不同最终幕 F1 入场触发新的成对表，跳过内容重复的表，平均合并完整表的卡牌增益；加牌支还可提供联合模型的合成行。合成证据保留独立标记，仅用于搜索分配。

`--feature-profile i082` 统一带齐上述配置及资源、路线与遥测机制，具体触发和证据限制见 [I082.md](I082.md)。iteration-082 已有 845/845 完整源码回归通过，整局效果按该版本的运行结果评估。

## 历史结果与新版本

本包保留 `frozen-i054a` / holdout-01 的完整汇总和 17 条获胜动作：20 个新种子各一次、每次 30 分钟，17 个独立重放确认胜利，3 个预算下 UNKNOWN。这是旧版本的 85% 观察解出比例（Wilson 95% 区间 64–95%）。[历史报告](../release/holdout-01/results.md)

i082 规划实现来自 `frozen-i082`，原冻结源码身份与公开构建适配分别记录。用户在自己的目录编译会生成新的宿主/solver/harness 字节身份，静态契约检查使固定源码构建可追踪；实际执行与胜利重放继续产生本机构建的独立证据。

本交付已经完成四项目源码编译和静态身份前置检查，该构建验证未执行原生游戏请求或胜利重放；前端另有本机零动作准备检查。[构建记录](../release/BUILD_VALIDATION.json) · [i082 来源](../release/i082/provenance.json)

## 在 SpireBoard 中使用

完成源码构建后，`tools/prepare_dashboard.py` 检查用户自己的构建身份与零动作宿主初始化，`dashboard/start.ps1` 启动本机浏览器页面。用户输入种子即可提交完整 i082 新作业，查看进展、资源、关口模型与获胜路线。

**暂停求解** 保存受控作业进程树的内存，暂停时不消耗主动预算；**继续求解** 恢复相同进程；**退出求解** 终止作业并保留已有记录。这让用户在进程存活期间控制计算，退出或机器重启后的恢复另需持久化能力。

前端本机准备的零动作检查不执行战斗或整局搜索。初始化、进程控制、真实求解与胜利重放分别保留验证记录。[前端说明](../dashboard/README.md)

当前证据范围为离线 TestMode 原生 DLL 执行。正常 Godot 游戏等价、不同游戏版本和其他平台按各自记录验证。失败或预算用尽保留 UNKNOWN，探针与模型只帮助分配下一批算力。
