# P0—P5 实现与审计说明

本实现把候选搜索与可核查证据分开。新的生产入口是 `spire_exact.planning`，原完整图枚举器仍作为小模型正确性基准。本文描述已写入代码的行为，不把后续研究计划冒充实现。

## P0：计时、身份与错误分类

`native/SpireNativeHost/PhaseProfiler.cs` 对嵌套阶段记独占墙钟时间（整数微秒），分开记录进程 CPU、分配量、GC 代数及工作集。阶段包括 bootstrap、恢复、菜单、已知动作执行、新动作执行、选项评估、Beam 搜索、续接比较、证据写入和检查点生成。

`planning/pool.py` 另记进程启动、排队、任务时间和采样峰值 RSS。并行任务的阶段耗时不能相加当总墙钟时间，进程累计 peak RSS 也不是单任务独占峰值。当前尚未接入全栈 EventPipe/PerfView 火焰图，不能把这些阶段计时说成完整 CPU 调用栈剖析。

`planning/archive.py::classify_failure` 区分路线死亡、预算耗尽、恢复/重放失配、宿主/机制缺口、超时、内存限制与未知。没有任何一个失败类别被用于推断种子不可通关。

`native.py` 和 `planning/identity.py` 绑定宿主源码、游戏核心 DLL、advisor 与依赖 bytes。相同路径替换镜像也不能沿用旧结果。源文件变动导致原生构建失效。SDK 包和私有游戏依赖使用上传包的来源，原上游 pin 不变。

## P1：两种复用，不混为搜索树复用

`CampaignReplay.Choose()` 的 history 分支直接校验并执行已记录的合法动作，绝不调用 `RankCandidate`。原项目已经有这个基本行为；本次增加计数、整合检查点跳过和分阶段测量，而不是宣称从零发明前缀回放。

`BeamAdvisor.cs` 读调用方预算/profile/DOP，去掉每回合无条件清空建议再重搜的硬编码。新回合通过 pinned CombatSolver 的 `ContinuationStamp.CaptureLive().StateText` 与预测续接做完整字符串比较。只有匹配才能使用后续动作；嵌套选牌、新战斗、实例部署映射或合法菜单失配会使路线失效。使用上游的部署实例映射而非只按卡名定位。

这实现的是**计划续用**；没有声称完整搜索树、所有转置表和挂起任务能跨根复用。某些复杂选择仍由原有候选器处理，之后必须失效续接。Beam 的容量、截断、镜像覆盖和启发式限制仍存在。

## P2：限定稳定地图边界的恢复

`RoomCheckpoint.cs` 存储原生 `RunManager.ToSave(null)`、完整动作前缀及证据、合法菜单、观测、上下文及二进制身份。对象键规范化比较完整 JSON；数组/牌序保持顺序。SHA 仅用于文件损坏检查，不替代完整语义 bytes 比较。

只在 `map` 阶段、无进行中的战斗、房间任务完成、有实际后续地图动作时捕获。商店、事件内部、任意回合中途和最终幕结算不直接快照，使用此前可靠边界加短动作后缀。

原生 DTO 的 `can_modify=false` 会被省略而恢复构造器默认 true；沿用显式序列化修正。空事件本地化变量字典在原生读回中会变 null，进行限定规范化。仅为当前布尔目标清除 clock、平台、地图绘图、reload 计数等表现/宿主字段；这些快照不可用来认证时间、分数或其他未建模目标。

本次实际发现并修复：`SetUpSavedSingleplayer` 会把 `RunManager.ShouldSave` 强制设为 true，但初始离线测试局是 false。恢复后显式还原为 false，避免结算时触发不同的存档、统计或原生平台副作用。没有修改卡牌数值、赠送资源或设置胜利标志。

恢复分三层验证：上下文/二进制/文件校验；原生恢复后规范化 save 全量相等；第一个稳定菜单及观测相等。验收再从不同检查点执行同一完整后缀，比较逐步证据。651 步检查点恢复后的最终胜利与从初始状态执行也一致。

`CheckpointArchive` 用完整动作前缀建立 trie，取最长合法祖先；不会只按楼层或 HP 复用状态。索引按 bytes 上限 LRU 淘汰，同时剪掉空 trie 分支。只移除索引，绝不删除用户证据文件。它不是从不同动作历史发现语义等价状态的通用转置引擎。

## P3：常驻、隔离、受预算控制的本地进程池

C# `--worker` 一次初始化 DLL，顺序消费请求文件路径。每个请求创建新的主循环上下文，结束后解绑观察器和奖励 selector，再调用原生清理。任务不健康时退出，后续独立任务另起进程；默认每 32 个任务轮换一次进程。

Python 每个 lane 持有一个 worker，隔离输出和临时目录，宿主使用内存存档，不碰个人存档。只有池拥有的进程会被关闭。管道结束、错误、RSS 超额和超时不会被伪造为游戏死亡；已修复关闭 broken pipe 掩盖首个错误的问题。

CPU 额度按 affinity/cgroup 有效额度与内存检测裁剪。DOP 本身也会裁剪，防止一进程申请过多内部线程。Linux 可用内存以宿主 MemAvailable 和 cgroup headroom 为边界，保守计入一半 inactive-file 可回收量；这是准入估计，不是 OS 硬限制。Windows 实现了 GlobalMemoryStatusEx/GetProcessMemoryInfo 路径，此次未实机验证。

同一时刻的原生任务受池大小限制。全局并发调度目前不动态迁移正在运行的 Beam，也不做 NUMA 绑核/GPU 加速。标定器输出建议，但不会在搜索途中擅自改变整个算法预算。已知固定恢复任务显示本环境外层两个 worker 更快，不能据此宣称所有硬件或搜索都线性扩展。

`ResultCache` 是按完整请求/规则身份记住一次真实可执行结果的有界缓存。Beam 时间预算下不同运行可能选不同候选，缓存命中不是“这个请求永远只有一个最优答案”。扩大预算或改策略会得到不同键。

## P4：失败点探测与向前扩窗

真实死亡后，从证据中提取该场战斗入场前缀，恢复至最近稳定点，给予 3 倍战斗预算再尝试。失败仍为“尚未找到”；不得把它升级成不可行证明。

探测成功会优先延伸该新可达状态。修复窗口逐步从最近一处局外决策扩到 2、4…直至配置上限，从记录过的真实合法选项生成替代前缀。改变动作之后不强迫沿用失效的旧后缀，而让原生游戏重新推进。不同候选的后续 RNG/奖励因此可以自然不同。

全局保留 HP 比例、资源、牌组规模、遗物和进度的多样性档案。描述子只用于调度与启发式保留，不构成状态等价、支配证明或下界。档案淘汰和候选上限都留下未知区域，上界维持 1。

这实现了失败驱动的具体反事实尝试，**没有自动生成可推广的因果定理或严格逻辑 Benders cuts**。所谓“窗口组合修复”来自逐次选择真实新路径再修改其上游，而非证明覆盖所有多决策组合。

## P5：局外短程 native rollout

统一比较 map、shop、rest、card_reward、event、select_cards、rewards、treasure 的合法动作。对每个备选先执行真实动作，再以有限预算模拟至配置楼层/动作界限；根据存活、进度和资源代理评分选出优质且不同的候选，加深搜索。

所有实际效果由上传版本的原生 DLL 执行；战斗可调用 Beam 建议。没有把假设直接变为“持有一张不存在的牌”。新卡数值和动作合法性来自当前模型，但 rollout 排序仍有手写规则，复杂新机制不保证自动取得好策略。

对限额之外动作只做延后/启发式舍弃，绝不称完整遍历。短程 utility 不是真实胜率，更不是可证明上界；没有完成整局 CEGAR/抽象上界收敛器。此阶段目标是生成并验证完整通关 witness。

## 胜利验收与信息边界

只有原生整局 `OnEnded(true)` 被观察且没有未处理错误时才可能成为获胜候选。另一个新进程、不带 advisor、不带检查点、不带缓存，从初始状态执行完整动作序列，要求终局和所有逐决策证据一致，才出具布尔目标 [1,1] 证据。

结算后 HP=0 不等于失败：该版本原生 `RunManager.WinRun()` 调用 OnEnded(true) 后执行 GuaranteeKillAllPlayers。我们的程序使用原生胜利回调而非终局 HP 猜测胜负；没有跳过这一步或手动赋胜利。

P5 是给定种子的全信息离线规划，可用反事实重试发现未来。不是首次公开信息策略，也不是接好了真实 STS2 的 POMCP。原有限信念模型仍单独保留，不能用它的测试成绩替代真实游戏泛化。

## 下一阶段的缺口

正常 Godot UI/原生 headless 全流程对照、未覆盖机制、真正跨种子/飞升的大样本胜率、任意战斗中途恢复、复杂搜索树持久化、更强的下游估值、保证完备的全局证明与 P6 都尚未完成。
